# AgriVision: SQLite → Supabase PostgreSQL Migration Plan

This document outlines the complete architectural migration from local SQLite databases (`data/products.db` and `data/rentals.db`) to a managed Supabase PostgreSQL instance, while preserving the existing FastAPI backend, ML inference pipeline, React frontend, and authentication behaviors.

---

## 1. Existing SQLite Schema

The existing application manages two separate SQLite database files defined in `utils/database.py`:

### `data/products.db`
```sql
CREATE TABLE IF NOT EXISTS products (
    code          TEXT PRIMARY KEY,
    product_name  TEXT NOT NULL,
    manufacturer  TEXT NOT NULL,
    batch         TEXT,
    expiry        TEXT,
    status        TEXT NOT NULL DEFAULT 'Verified',
    product_type  TEXT,
    registered_on TEXT
);
```

### `data/rentals.db`
```sql
CREATE TABLE IF NOT EXISTS users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    role          TEXT NOT NULL CHECK (role IN ('farmer', 'owner')),
    full_name     TEXT,
    phone         TEXT,
    location      TEXT,
    created_at    TEXT
);

CREATE TABLE IF NOT EXISTS machines (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    name         TEXT NOT NULL,
    machine_type TEXT,
    hourly_rate  REAL NOT NULL,
    daily_rate   REAL NOT NULL,
    location     TEXT,
    owner_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    description  TEXT,
    available    INTEGER NOT NULL DEFAULT 1,
    created_at   TEXT,
    updated_at   TEXT
);

CREATE TABLE IF NOT EXISTS bookings (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    machine_id  INTEGER NOT NULL REFERENCES machines(id) ON DELETE CASCADE,
    farmer_id   INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    start_date  TEXT NOT NULL,
    end_date    TEXT NOT NULL,
    total_cost  REAL,
    status      TEXT NOT NULL DEFAULT 'confirmed',
    notes       TEXT,
    created_at  TEXT
);
```

## 2. Supabase PostgreSQL Schema

The converted schema is saved in `backend/supabase_schema.sql`. It converts SQLite dynamic types to strict, idiomatic PostgreSQL types and establishes identity columns, constraints, foreign keys with cascade behavior, and helpful composite views.

```sql
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

CREATE TABLE IF NOT EXISTS products (
    code          TEXT PRIMARY KEY,
    product_name  TEXT NOT NULL,
    manufacturer  TEXT NOT NULL,
    batch         TEXT,
    expiry        DATE,
    status        TEXT NOT NULL DEFAULT 'Verified',
    product_type  TEXT,
    registered_on TIMESTAMPTZ DEFAULT timezone('utc'::text, now())
);

CREATE TABLE IF NOT EXISTS users (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username      TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    role          TEXT NOT NULL CHECK (role IN ('farmer', 'owner')),
    full_name     TEXT,
    phone         TEXT,
    location      TEXT,
    created_at    TIMESTAMPTZ DEFAULT timezone('utc'::text, now())
);

CREATE TABLE IF NOT EXISTS machines (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name         TEXT NOT NULL,
    machine_type TEXT,
    hourly_rate  NUMERIC(10, 2) NOT NULL,
    daily_rate   NUMERIC(10, 2) NOT NULL,
    location     TEXT,
    owner_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    description  TEXT,
    available    BOOLEAN NOT NULL DEFAULT TRUE,
    created_at   TIMESTAMPTZ DEFAULT timezone('utc'::text, now()),
    updated_at   TIMESTAMPTZ DEFAULT timezone('utc'::text, now())
);

CREATE TABLE IF NOT EXISTS bookings (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    machine_id  BIGINT NOT NULL REFERENCES machines(id) ON DELETE CASCADE,
    farmer_id   BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    start_date  DATE NOT NULL,
    end_date    DATE NOT NULL,
    total_cost  NUMERIC(10, 2),
    status      TEXT NOT NULL DEFAULT 'confirmed',
    notes       TEXT,
    created_at  TIMESTAMPTZ DEFAULT timezone('utc'::text, now())
);
```

| `product_type` | TEXT | `product_type` | TEXT | Fungicide, Bio-pesticide, Fertilizer, etc. |

## 4. Existing Database Functions → Future Repository Functions

All direct SQLite SQL statements currently run via `fetch_one`, `fetch_all`, and `execute` have been wrapped into clean, typed repository classes in `backend/database/repositories.py`:

| Operation / Feature | Current SQLite Implementation | Future Supabase Repository Function |
| :--- | :--- | :--- |
| **Verify product code** | `fetch_one(..., "SELECT * FROM products WHERE code = ?", ...)` | `ProductRepository.get_by_code(code)` |
| **List product registry** | `fetch_all(..., "SELECT ... FROM products ORDER BY code ...", ...)` | `ProductRepository.list_all(limit)` |
| **Product count** | `product_registry_count()` / `SELECT COUNT(*) FROM products` | `ProductRepository.count()` |
| **Insert product** | Direct `INSERT INTO products` | `ProductRepository.insert(product)` |
| **User lookup (ID)** | `fetch_one(..., "SELECT * FROM users WHERE id = ?", ...)` | `UserRepository.get_by_id(user_id)` |
| **User lookup (Username)** | `fetch_one(..., "SELECT * FROM users WHERE username = ?", ...)` | `UserRepository.get_by_username(username, include_password_hash=...)` |
| **User registration** | `execute(..., "INSERT INTO users ...", ...)` | `UserRepository.create(username, password_hash, role, ...)` |
| **User count** | `SELECT COUNT(*) FROM users` | `UserRepository.count()` |
| **List machines** | `fetch_all(..., MACHINE_SELECT + filters, ...)` | `MachineRepository.list_machines(location, type, owner, available)` |
| **Machine detail** | `fetch_one(..., MACHINE_SELECT + "WHERE m.id = ?", ...)` | `MachineRepository.get_by_id(machine_id)` |
| **Create machine** | `execute(..., "INSERT INTO machines ...", ...)` | `MachineRepository.create(owner_id, name, ...)` |
| **Update machine** | `execute(..., "UPDATE machines SET ... WHERE id = ...", ...)` | `MachineRepository.update(machine_id, owner_id, updates)` |
| **Delete machine** | `execute(..., "DELETE FROM machines WHERE id = ...", ...)` | `MachineRepository.delete(machine_id, owner_id)` |
| **Check booking clash** | `fetch_one(..., BOOKING_SELECT + date range clash, ...)` | `BookingRepository.find_overlapping(machine_id, start_date, end_date)` |
| **Create booking** | `execute(..., "INSERT INTO bookings ...", ...)` | `BookingRepository.create(machine_id, farmer_id, start, end, cost, notes)` |
| **List bookings (farmer)** | `fetch_all(..., BOOKING_SELECT + "WHERE b.farmer_id = ?", ...)` | `BookingRepository.list_for_farmer(farmer_id)` |
| **List bookings (owner)** | `fetch_all(..., BOOKING_SELECT + "WHERE m.owner_id = ?", ...)` | `BookingRepository.list_for_owner(owner_id)` |
| **Cancel booking** | `execute(..., "UPDATE bookings SET status = 'cancelled' ...", ...)` | `BookingRepository.cancel(booking_id, user_id)` |
| **Marketplace status** | `rental_db_status()` | `backend.database.rental_database_status()` |

## 5. Authentication & Password Handling

The application's authentication uses:
- **Algorithm:** Salted `PBKDF2-SHA256`
- **Iterations:** 120,000
- **Salt:** 16-byte random hex string (`secrets.token_hex(16)`)
- **Digest Format:** `pbkdf2_sha256$<iterations>$<salt>$<hex_digest>`
- **Comparison:** Constant-time equality (`hmac.compare_digest`)
- **Session Tokens:** HMAC-SHA256 signed bearer tokens managed in `backend/security.py`

### Migration Strategy:
1. **Preserve exact hash format:** Existing password hashes are standard string digests and are stored directly in PostgreSQL's `users.password_hash` text column.
2. **Zero password reset requirements:** Users do not need to reset passwords because `backend.database.verify_password` operates identically against PostgreSQL records.
3. **No plaintext passwords:** Plaintext passwords are never stored in `backend/supabase_seed.sql` or database tables.

## 7. Environment Variables

Add the following to `.env`:

```bash
# Supabase PostgreSQL Database Credentials
SUPABASE_URL=https://<your-project-id>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOi...<your-service-role-key>
```

### Security Directives:
- **Never expose `SUPABASE_SERVICE_ROLE_KEY` to the browser or React frontend.**
- The service role key is reserved for server-side FastAPI endpoints to manage user records and execute admin-level database operations.
- Ensure `.env` is listed in `.gitignore` (already verified).

## 8. Files Requiring Modification During Actual Migration

When the migration is executed (cutover phase), only the following application files will need adjustment:

1. **`backend/main.py`**
   - Replace `from utils.database import init_products_db, init_rental_db` with Supabase connection health check in `lifespan()`.
2. **`modules/product_verifier.py`**
   - Replace direct `fetch_one` / `fetch_all` queries with `ProductRepository.get_by_code()` and `ProductRepository.list_all()`.
3. **`modules/equipment_rental.py`**
   - Replace direct `fetch_all` / `execute` calls with `UserRepository`, `MachineRepository`, and `BookingRepository` methods.
4. **`backend/test_api.py`**
   - Update tests to clean up created entities via repository calls or mock database client when running against Supabase.

*All other parts of the system (ML models, PyTorch, Gemini API, frontend React components, styling) remain completely untouched.*

## 9. Migration Execution Order

1. **Phase 1: Supabase Setup**
   - Create a new project in the Supabase Dashboard.
   - Run `backend/supabase_schema.sql` in the Supabase SQL Editor.
   - Run `backend/supabase_seed.sql` to populate demo products, users, and machines.
2. **Phase 2: Environment Configuration**
   - Copy `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` into `.env`.
   - Run `python -c "from backend.database import check_connection; print(check_connection())"` to confirm network connectivity.
3. **Phase 3: Module Cutover**
   - Update `modules/product_verifier.py` to use `ProductRepository`.
   - Update `modules/equipment_rental.py` to use `UserRepository`, `MachineRepository`, `BookingRepository`.
   - Update `backend/main.py` lifespan to verify Supabase connection.
4. **Phase 4: Test & Validate**
   - Run `pytest backend/test_api.py` to verify API routes, authentication, machine listings, and booking overlap prevention.
5. **Phase 5: Cleanup & Archival**
   - Archive `data/products.db` and `data/rentals.db` to a backup location.
   - Deprecate `utils/database.py`.

---

## 10. Rollback Considerations

- **Dual-Storage Isolation:** Because `utils/database.py` and the SQLite databases remain completely untouched during preparation, reverting is instantaneous: set a config flag to revert back to SQLite if the remote Supabase instance experiences latency or connection downtime.
- **Warm SQLite Backup:** Before initiating Phase 3 cutover, take a snapshot backup of `data/products.db` and `data/rentals.db`.
- **Database Abstraction Layer:** The repository design in `backend/database/` allows switching backends without touching endpoint schemas or React interfaces.
